**两件都成立，且各有活读数**：同一 task 被人类第二次派发、再失败时**会再得到一次自愈**（实测 4 个 run：两代 × 〔一次尝试 + 一次自愈〕，每代恰好一次）；daemon 在 spawn 带 origin 的 run 时注入 `RUAGENT_CHAT_ID`，`task_dispatch` 缺省继承它、显式值优先、无 origin 时该变量**不存在**（不是空串）。门禁：`clippy` exit 0，`test --workspace` exit 0（ok 91 / FAILED 0 / passed 964）。

## ② P5 实现点

### 判据（只有一处）

`crates/daemon/src/runs.rs:2302` `fn heal_budget_spent(runs, ending) -> bool`：

```
current = ending.params.dispatch_epoch
没有 current（旧行）        → 簇里任何 self_heal_of 都算预算已用
有 current                  → self_heal_of.is_some()
                              && dispatch_epoch.is_none_or(|h| h == current)
```

- 「本世代」= **正在收尾的那个 run** 的 `dispatch_epoch`；`is_none_or` 就是兼容规则（`None`＝无法归属 ⇒ 算作本代 ⇒ **不多给预算**）。
- 调用点唯一：`finish_cluster` 的 (4) 分支 `runs.rs:2231`（`let healed_already = heal_budget_spent(&runs, run);`）。旧写法 `runs.iter().any(|r| r.params.self_heal_of.is_some())` 已删除，全仓不再有第二個读者。

### 兼容性注释在哪

- `crates/core/src/run.rs:159-179` `RunParams::dispatch_epoch` 的 doc：讲清「旧行 `None` ⇒ 视为同一世代 ⇒ 不额外给预算」以及**为什么朝保守方向**（静默多烧一轮用户的 token 是错得更贵的那个方向）。字段是 `#[serde(default, skip_serializing_if = "Option::is_none")]`，落在 `runs.params` 这个 JSON 列里，**没有迁移**。
- `runs.rs:2290-2301` `heal_budget_spent` 的 doc 第二段复述同一条规则（读代码的人有两处会看到，说法一致）。

### 世代的产生（谁决定这个数字）

- 新增 `runs.rs:160` `enum DispatchEpoch { New, Of(Option<u32>) }`：`New` = 刚落的一次人类派发（`start_run` 自己编号），`Of(..)` = 属于已存在的一代。**为什么需要这个类型**：一个 fan-out 的 N 个分支是**一次**派发，若让每个分支各自 `count()` 会得到 0/1/2 三个「世代」，于是每支一个自愈预算 —— 那正是 P5 要修的 bug 换了件衣服。所以 `start_fanout` 只算一次（`runs.rs:1162`）再发给每个分支。
- `runs.rs:753` `start_run` 里赋值；`runs.rs:1008` `next_dispatch_epoch` = 该 task 已有**非自愈** run 数（从 0 起；旧行照样计入 —— 它确实是一次派发）。
- 自愈继承（`runs.rs:1130`）：`self_heal` ⇒ `Of(old.params.dispatch_epoch)`；人类一键 retry（`retry_run`，`self_heal=false`）⇒ `New`（重派＝新一代，有预算）。
- 报告文案（`runs.rs:2412`）：`（含 N 次自愈重试）` 改为**数 attempt 上的 heal 行**，因为一个簇现在可能有两代、两次自愈，写死「1 次」会是假话。`supervise_wakeup.rs` 既有的「含 1 次自愈重试」断言仍然成立（它那个簇只有一代）。

### 实测（`crates/daemon/tests/heal_generations.rs`）

- `a_second_dispatch_of_the_same_failing_task_gets_its_own_self_heal`：派发 1 → 2 个 run（epoch 0,0）；人类再派发 → 4 个 run（epoch 0,0,1,1）；heal 行 = 2，每代恰好 1；task 回到 `pending`；settle 窗口后**不再增长**。
- `a_pre_versioning_heal_row_still_counts_as_this_generation`：手工写入两条**无** `dispatch_epoch` 的旧行（一条是 heal，经 daemon 自己的 `Db` 句柄 —— 单写入者，不新开连接），再派发一次 → 3 个 run，**没有**第四个 ⇒ 旧数据不多给预算。

## ③ P6 实现点

### spawn env 的确切位置

1. **生产者**：`crates/daemon/src/runs.rs:1681`（`supervise` 里、`RunOptions` 构造之前）—— 有 origin 才 push `(ruagent_core::CHAT_ID_ENV, origin_chat_id)`；`trim` 后为空也算没有。
2. **落地**：`crates/acp/src/run.rs:90` —— `run_once` 现在用
   `AcpAgent::new(AcpAgentConfig::new(program).args(args).envs(opts.env))`
   （原来是 `AcpAgent::from_args(...)`，那个入口无法表达环境变量）。`AcpAgentConfig::envs` 是**追加**到继承来的环境之上，不清空（清空会带走 PATH / 系统代理 / `RUAGENT_URL`）。
   `RunOptions::env`（`acp/run.rs:49`）是唯一入口，注释里写明「无 origin 时是空 Vec，变量必须缺席而不是空串」。
3. **MCP server 那一跳**：不是显式代码 —— 平台 MCP server 是**agent 自己**在 `session/new` 时 spawn 的，因此继承 agent 的环境。这是 OS 语义，也是本仓库既有的 `RUAGENT_URL` 一直在依赖的同一机制（`crates/mcp/src/lib.rs:32` 读它）。
4. **已知泄漏，写进注释也写进报告**：`AcpAgentConfig` 只能加不能删，所以如果 **daemon 自己**是被某个 agent 进程启动的（环境里已有同名变量），无 origin 的 run 会看到那个继承值。删需要清空环境，代价更大，因此留着可见而不是糊过去（`runs.rs:1673-1680`）。

### `task_dispatch` 的读取顺序（`crates/mcp/src/lib.rs:698`）

```
显式 params.origin_chat_id（trim 后非空）      → 用它
否则 RUAGENT_CHAT_ID（本进程环境）             → 用它
否则                                          → 请求 body 里**不写** origin_chat_id 这个键
```

- `mcp/lib.rs:2661` `const CHAT_ID_ENV: &str = "RUAGENT_CHAT_ID";` 是 `core::CHAT_ID_ENV` 的**文档化副本**：`ruagent-mcp` 故意不依赖 `ruagent-core`（该 crate 里 `TERMINAL_RUN_STATUSES` 已经是同一先例），所以在两侧各留一份并交叉引用，而不是悄悄加一条依赖。空串按「没有」处理（daemon 从不写空串，`RUAGENT_CHAT_ID=` 是 shell 事故）。
- 回复里多一行（`mcp/lib.rs:2679` `dispatched_to_text` 新增 `origin` 参数）：
  `belongs to conversation: <id> -- …` ／ `belongs to NO conversation: nobody is waiting to be told when this ends …`。理由：P6 把「填 origin」从调用方手里拿走了，那么「这次到底有没有人在等」就必须回给调用方，否则 agent 会以为自己报过。

### 描述改成什么（工具描述，`mcp/lib.rs:668`）

新增的句子（原文）：

> REPORTING BACK: the conversation you are running in is attached to the work AUTOMATICALLY (the daemon exports it to this process as RUAGENT_CHAT_ID and this tool forwards it), so you do not have to know your own chat id and normally must not pass origin_chat_id at all; an explicit origin_chat_id you DO pass wins over it. A run started with no conversation behind it (the panel, the CLI, a script) carries no such variable, so the work it dispatches is reported to nobody -- that is correct, because nobody is waiting.

参数说明（`TaskDispatchParams::origin_chat_id`）同步改成「你通常不用传、显式优先、无会话归属时不唤醒」。

### 实测

- `crates/daemon/tests/chat_origin_env.rs::a_chat_dispatched_run_carries_its_conversation_and_an_unattributed_one_carries_nothing`（真进程）：
  ```
  env RUAGENT_CHAT_ID=<01a20920-4dcc-71c6-8705-8efbf41ebced> pid=59492 child=<01a20920-4dcc-…>
  env RUAGENT_CHAT_ID=<unset>                              pid=46248 child=<unset>
  ```
  即：带 origin ⇒ 变量在、值就是那个会话、**子进程也继承**；无 origin ⇒ `<unset>`（不是 `<>`）。
- `crates/mcp/tests/dispatch_origin.rs::task_dispatch_attributes_work_to_the_conversation_the_daemon_exported`：同一个工具、同一个进程、三种环境状态依次走 —— 无环境 ⇒ wire 上无 `origin_chat_id`；有环境 ⇒ wire 上等于它；显式参数 ⇒ 覆盖环境；`RUAGENT_CHAT_ID=`（空）⇒ 按缺席处理。
- `…::the_dispatch_description_says_the_conversation_is_automatic`：描述里确实有 `RUAGENT_CHAT_ID`、`AUTOMATICALLY`、`explicit  … wins`、`reported to nobody`。

## ④ 「一个 run 一个进程」的读数

**是这个形态，所以「一个进程一个 `RUAGENT_CHAT_ID`」成立。**

- 代码：`crates/acp/src/lib.rs:3-6` 的模块 doc —— *"connection-per-run: spawn a fresh agent subprocess per run"*；`runs.rs` 的 `supervise` 对一次 run 只调一次 `run_once`；`run_once` 每次调用构造一个 `AcpAgent`。
- **实测**：上面那次运行里两个 run 的 agent 自报 pid 是 **59492 / 46248**（不同）；`child=<同一个 chat id>` 说明继承链在（这正是「子 agent 在同一会话里干活」期望行为）。
- 边界（这也是规格 §3 风险段要我确认的）：**chat 会话**是「一个 chat 一个进程、长期复用」（`daemon/chat.rs` 的 `start_inner` → `start_chat` 一次，之后多轮提示词都在这一个进程里）。一个 chat 就是一个会话，所以「一个进程只服务一个会话」仍然成立；但注意那个进程目前**没有**被注入（见 ⑦a），所以这条边界今天是「没被用上」，不是「被违反」。
- 另外：`RUAGENT_CHAT_ID` 会被 agent 传给它的**所有**子进程 —— 这是期望行为（子 agent 也在同一会话里干活），实测读数就是 `child=<chat id>`。

## ⑦ 没做到 / 没覆盖（照实写）

**a. 会话侧（chat.rs 的 agent 进程）没有注入 `RUAGENT_CHAT_ID` —— 这是 P6 最想要的那一跳。**
P6 的触发器是「主 agent 在一个会话里派活」，那个 agent 进程是 `chat.rs:1129` 的 `start_chat(ChatOptions{…})`，不是 run。今天的实现只覆盖 **run 侧**（子 agent 的二级派发仍然正确归属）。要补的两步都很小，但**第二步在禁碰文件里**，且第一步会让他们的 `ChatOptions{…}` 字面量立刻 `E0063`（两人同时改同一处必冲突），所以我没做：
1. `crates/acp/src/chat.rs`：`ChatOptions` 加 `pub env: Vec<(String, String)>`，`start_chat` 里照 `run_once` 用 `AcpAgentConfig::envs(opts.env)`（今天 `start_chat` 仍是 `AcpAgent::from_args`，同样无法带 env）。
2. `crates/daemon/src/chat.rs` 的 `start_inner`：`env: vec![(ruagent_core::CHAT_ID_ENV.to_string(), id.to_string())]`（`id` 就是那个 chat 的 id，`start_inner` 里已存在）。
这两步落地后，会话里派出去的第一跳也会自动归属；在那之前，「主 agent 会汇报」的第一跳仍然要靠调用方显式传 `origin_chat_id`。

**b. 「agent 自己调 `task_dispatch`」没有真的端到端跑通。** `rustagent-mock-agent` 既不 spawn MCP server 也不说 MCP 客户端协议，我没有为了这个虚构一条链路。我交的是**三层分开的读数**，并明确它们不是一条链：
1. daemon → agent 进程的环境（真进程，`env RUAGENT_CHAT_ID=<chat>`）；
2. agent → 它的子进程继承（`child=<chat>`，同一次读数）；
3. MCP 工具读环境并在 wire 上带 origin（同进程、真 HTTP mock daemon 观测 body；显式/缺省/空三种都测）。
中间那一跳（agent spawn 平台 MCP server）依据 OS 继承 + `RUAGENT_URL` 这个**既有的、在用的**同类依赖，不算读数。

**c. P5 的负控（把 `heal_budget_spent` 暂时改回旧判据，看新测试是否变红）没有真跑。** 那会让共享树在窗口内变红（本仓库明令：负控要么在隔离 worktree 里、要么先声明）。我的说法是**推导不是读数**：旧判据下第二次派发时簇里已有第 0 代的 heal 行 ⇒ 不再自愈 ⇒ 簇停在 3 个 run，而 `settle(want=4)` 会超时并 panic。

**d. 并发派发未测。** 同一 task 几乎同时两次派发可能读到同一个 `count` ⇒ 两个 run 拿到同一个 epoch（共享一个预算，而不是各一个）。方向是保守的（少自愈而不是多自愈），但没有测试钉住。

**e. 人类一键 retry（`POST /runs/{id}/retry`）算「新的一代」⇒ 有新的自愈预算。** 这是有意的（重派＝想要它成），但没有专门测试。

**f. 旧数据那条测试在旧代码上也绿。** 它钉的是**兼容规则**（旧 heal 行不给新预算），不是 P5 的判别式；判别式只有「第二次派发仍自愈」那一条。

**g. 只有 Windows 读数。** `mock-agent` 的 child 探针有 `cfg(windows)` / `cfg(not(windows))` 两版（`cmd /c echo %VAR%` 与 `sh -c 'printf %s "${VAR}"'`），unix 版没在本机跑过（WSL 没有工具链，见 AGENTS.md）。

**h. 一处环境细节值得记一笔**：`AcpAgentConfig::envs` 只能加不能删，所以「daemon 自己被 agent 启动」时继承来的同名变量会漏到子进程。今天的 daemon 是 WMI 启动、干净环境，但这条路径没有测。
