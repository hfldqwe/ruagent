## 2. Multi-Agent: Teams & Workflows

### Teams — leader/member model

`Team(members=[Agent|Team, ...], model=..., mode=...)`. Teams nest (sub-teams get their own leader). Leader and members each make **separate model calls** (docs are explicit about the added latency/token cost). Members without an explicit model inherit the team's model.

**Coordination modes** (`TeamMode` enum; legacy flags `respond_directly`/`delegate_to_all_members` map to route/broadcast and are overridden by `mode`):

| Mode | Behavior | Use case |
|---|---|---|
| **Coordinate** (default) | Leader decomposes, formulates a per-member task, delegates, synthesizes results | Open-ended work needing quality control |
| **Route** | Leader picks ONE member and returns its response directly (no synthesis). `determine_input_for_members=False` = full passthrough | Specialist routing, low latency |
| **Broadcast** | Same task to every member; sync = sequential, async = concurrent; leader reconciles | Independent perspectives (bias reduction) |
| **Tasks** | Autonomous loop: leader builds and executes a **shared task list** with task-management tools until goal complete or `max_iterations` | Multi-step decomposed jobs |

Note: v1's `collaborate` mode (members talking to each other) is **gone**. Coordination is strictly **leader-mediated** — members do not call each other peer-to-peer; the leader selects members, writes their tasks, and synthesizes. Member selection/tracking uses member IDs.

**How members get context / shared state:**

- `session_state` dict is stored with the team session; **callable factories** for `members`, `tools`, and `knowledge` are resolved at run setup *after* session state loads, and receive injected parameters by name (`agent`/`team`, `run_context` (user_id, session_id, session_state), `session_state`). Factory results cached by custom key > `user_id` > `session_id` (`cache_callables=False` to re-resolve every run). This is the dynamic-composition mechanism: membership itself can depend on session state.
- `store_member_responses=True` persists each member's run with the team's run record; `member_responses` on the output; member events forwarded in streams by default.
- Teams support the same feature surface as agents: db, knowledge (leader searches it), memory, reasoning, tools, skills, guardrails, structured I/O.

**Critical limitation for heterogeneous platforms:** members must be **native Agno Agents/Teams**. External-framework adapters (`ClaudeAgent`, `LangGraphAgent`, `DSPyAgent`, `AntigravityAgent`) satisfy `AgentProtocol` for AgentOS serving (registration, routing, streaming, session records) but **cannot be Team members or Workflow step executors**, and get none of Agno's memory/knowledge/delegation/hooks (see §7).

### Workflows — deterministic step graphs

`Workflow(name=..., steps=[...])` (keyword-only in v3). A `Step` wraps exactly one executor: **Agent | Team | Python function | nested Workflow** (auto-wrapped when passed directly). Containers: `Steps` (named group), `Parallel`, `Loop` (until condition or `max_iterations`, optional `forward_iteration_output`), `Condition` (branch, `else_steps`), `Router` (runtime selector with `step_choices`).

- **Data flow:** function steps access any prior output via `StepInput` (`get_step_content(name)`, `get_all_previous_content()`); agent/team steps receive the most recent output. `additional_data` passes metadata to steps. Structured I/O at each step (Pydantic-validated agent output passed between steps), `input_schema` validates workflow input.
- **"Fully Python" mode:** replace `steps` with a single function that controls the whole run.
- **Conversational workflows:** `WorkflowAgent` routes messages between workflow history and execution.
- **Workflow Tools:** expose a workflow to any Agent/Team via a `run_workflow` tool — workflows are first-class callable components.
- **HITL (the standout design):** three pause levels — step-level (confirm/user-input/output-review/route-selection, incl. per-Loop-iteration review), executor-level (a tool *inside* an agent pauses), and nested (both). Pause state is **persisted to the workflow's db**; resume via `workflow.continue_run(run_output)` after resolving `StepRequirement` objects (`req.confirm() / reject(feedback=...) / set_user_input(...) / select(...)`). `on_reject` ∈ {skip, cancel, retry, else_branch}; timeouts with `on_timeout` ∈ {approve, skip, cancel}. v3 consolidated all flat HITL kwargs into one `HumanReview(...)` config.
- **Background execution:** `background=true` → `202 Accepted` + polling. v3 adds a **durable queue** (`agno_jobs`): accepted runs are committed rows that survive crashes/restarts/deploys and are executed by any replica; bounded concurrency (default 32), cancellable while queued, `Idempotency-Key` dedupe, 429 on full queue. Redis is optional coordination, never truth.
- **Teams vs Workflows:** leader-decided flow (adaptive) vs declared step graph (repeatable, explicit error policy per step).

## 3. Agent Knowledge

`Knowledge(vector_db=..., contents_db=db)` — one generic solution for many content forms (v2 collapsed `AgentKnowledge` into this).

**Architecture — two stores:**

1. **Contents DB** (relational, e.g. `agno_knowledge` table): content metadata — name, description, metadata, type, size, `access_count`, status, `external_id` (for external stores like LightRAG). Powers the AgentOS knowledge UI and status tracking.
2. **Vector DB**: chunk embeddings + similarity search.

**Ingestion pipeline:** reader parses (PDF, Docling, CSV, JSON, Markdown, website crawler, `llms.txt` index, YouTube transcripts, raw text, topics) → chunking strategy splits → embed → store. Sources also include cloud storage (S3, GCS, SharePoint, GitHub, Azure Blob). API: `insert()` / `ainsert()` / `ainsert_many()` (v3 removed `add_content*`).

**Chunking strategies (9):** Fixed (chars + overlap), Semantic (embedding-similarity boundaries, configurable threshold), Recursive (separator hierarchy), Document (paragraph→sentence), Markdown (heading-aware), CSV-row, **Agentic** (model finds breakpoints), **Code** (AST boundaries via Chonkie), Custom (subclass `ChunkingStrategy`). Configurable per-reader.

**Vector DBs (19):** PgVector, SingleStore, ClickHouse, Pinecone, Qdrant, Weaviate, Milvus, Chroma, MongoDB Atlas, Azure Cosmos, Redis, Valkey, Couchbase, Cassandra, SurrealDB, LanceDB (local, hybrid FTS), Upstash, LightRAG (graph RAG), plus bridges to existing LangChain vectorstores and LlamaIndex indexes.

**Retrieval:**

- **Agentic RAG is the default**: attaching `knowledge` to an Agent registers a `search_knowledge_base` tool (`search_knowledge=True` by default) — the model decides when/what to search. `add_knowledge_to_context=True` gives traditional RAG (retrieve before first model call).
- Search types: `vector` / `keyword` / `hybrid` (per-DB support); rerankers (e.g. Cohere) composable.
- **Filters**: metadata filters incl. expression forms (EQ/AND/OR/NOT); `knowledge_filters` at run time; per-user isolation of knowledge in v3 (unowned knowledge = shared: readable by all, editable by admin).
- **Custom retriever**: `knowledge_retriever` function replaces the whole `Knowledge.retrieve()` path (query rewriting, external recall, etc.).
- `KnowledgeTools` (reasoning integration): `think`, `search_knowledge`, `analyze` — agent reasons about search results before answering.
- **Published Pages** mode: for doc sites — keeps published Markdown and search vectors in sync, supports searching sections and reading the exact page revision behind a result (docs agent pattern).
- **Agents can WRITE knowledge**: `knowledge.insert(name, text_content)` from a tool — the learned-knowledge loop (below) is built on this.
- Teams: team-level `knowledge` is searched by the leader; "distributed RAG" patterns coordinate members over different vector/hybrid tables in one database.
- `knowledge` accepts **callable factories** (resolved per run with session context).

## 4. Agent Memory (in detail)

Agno currently has **two coexisting memory layers**: the classic v2 `MemoryManager` API (still supported on the constructor) and the newer **Learning Machines** subsystem (`agno.learn`, arrived during the 2.x line, now the flagship and the only surface Studio authors). v3 renamed the classic flags: `enable_user_memories` → `update_memory_on_run`, `search_session_history` → `search_past_sessions`.

### 4.1 Classic memory (MemoryManager)

Two mutually exclusive modes (agentic wins if both set):

- **Automatic** — `update_memory_on_run=True`: one `MemoryManager` extraction call per run, run in a **background thread** outside the conversation; memory instructions/tools stay out of the main context. Extraction can add/update/delete memories.
- **Agentic** — `enable_agentic_memory=True`: the agent gets an `update_user_memory` tool. Each call fires a **nested LLM call** that loads *all* existing user memories into context — the documented "agentic memory token trap" (their worked example: a 10-message conversation with 7 memory updates ≈ **8× token cost**; 200 memories ⇒ 10k+ tokens per update). Mitigations from their best-practices page: prefer automatic mode, give `MemoryManager` a **cheaper model** than the conversation model, instruct against frivolous updates, prune old memories, `tool_call_limit`.

`MemoryManager(model=..., db=..., additional_instructions=...)`:

- **Write**: `add_user_memory(UserMemory(memory=..., metadata=...))` — also standalone from text or a message list.
- **Read**: `get_user_memories(user_id=...)`; `search_user_memories(user_id, limit, retrieval_method=)` with `last_n` / `first_n` / **`agentic`** (a model selects memories related to a query).
- **Optimization/summarizers**: `optimize_memories(user_id, strategy=MemoryOptimizationStrategyType.SUMMARIZE, apply=False|True)` — LLM compacts a user's memories into one summary; `apply=False` previews. Custom strategies via `MemoryOptimizationStrategy` subclass. Token counting built in (`SummarizeStrategy.count_tokens`).
- Deletion gated by manager flags (`MemoryManager(delete_memories=True, clear_memories=True)` enables agentic delete/clear; automatic path always exposes add/update/delete).
- `add_memories_to_context=False`: collect memories in the background without injecting them (for analytics or tool-only access).
- `MemoryTools(db=...)`: standalone CRUD toolkit attachable to any agent.

**Storage & sharing:** memories live in the `agno_memories` table (custom name via `memory_table`/`memory_collection`) scoped by `user_id` (default `"default"` — the documented pitfall). **All agents, teams, and workflows connected to the same database share memories for a given user automatically** — cross-agent memory sharing is by construction, not per-agent wiring.

**Session summaries** (separate feature): `enable_session_summaries=True` + `SessionSummaryManager` maintains a rolling LLM summary per session (use a cheap model); `add_session_summary_to_context=True` injects it; composable with a small raw-history window (`add_history_to_context`, `num_history_runs`).

### 4.2 Learning Machines (`agno.learn`) — the current architecture

`Agent(learning=True)` (enables User Profile + User Memory in Always mode) or fine-grained:

```python
Agent(learning=LearningMachine(
    user_profile=True,       # structured facts, per user
    user_memory=True,        # unstructured observations, per user
    session_context=True,    # goals/plan/progress, per session
    entity_memory=EntityMemoryConfig(namespace="global"),
    learned_knowledge=True,  # insights across users (needs Knowledge + vector db)
    decision_log=True,       # decisions + outcomes, per agent
))
```

**Six typed stores** behind one uniform protocol — each implements `recall`, `process`, `build_context`, `get_tools`:

| Store | Captures | Scope | Default mode | Agentic tools |
|---|---|---|---|---|
| **User Profile** | Structured fields (name, preferred_name + custom dataclass schema with `metadata["description"]` per field) | per user | Always | `update_profile` |
| **User Memory** | Unstructured observations ("prefers code examples", "works on ML project") | per user | Always | `update_user_memory` |
| **Session Context** | Summary + optional planning (goal / plan / progress); **snapshot replaced each update**, not appended | per session | Always | — |
| **Entity Memory** | Entities with **facts / dated events / relationships** (typed graph); fact supersession via model judgment (`supersession_threshold=0.8`); archive/revive | global / user / custom namespace | Agentic only | `remember_about`, `link_entities`, `search_entities`, `forget` |
| **Learned Knowledge** | Reusable cross-user insights (title/learning/context/tags); semantic search | global / user / custom namespace | Agentic | `search_learnings`, `save_learning` |
| **Decision Log** | decision / reasoning / alternatives / confidence / **outcome + outcome_quality** (feedback loops) | per agent | Agentic only | `log_decision`, `record_outcome`, `search_decisions` |

**Learning modes (per store):**

- **Always** — extraction starts **concurrently with the main model call**, from the input snapshot (it sees conversation up to the current user message, not the current response). Cost: one extra LLM call per enabled store per run.
- **Agentic** — store-specific tools; the model decides. May miss implicit info.
- **Propose** — model proposes and waits for user confirmation; **prompt-enforced only** (the `save_learning` tool remains available; docs explicitly warn not to use it as the sole approval control for regulated workflows).

**How memory flows during a run:**

- **Write path:** Always-mode extraction runs in background off the input snapshot; Agentic-mode writes happen mid-run via tools (nested LLM call). Entities have no extraction pass — writes only via `remember_about`.
- **Read path:** `recall` → `build_context` → injection into the system prompt as **tagged, bounded blocks**: `<user_profile>`, `<user_memory>`, `<session_context>` (summary/goal/plan/completed), `<relevant_learnings>` (semantically retrieved, "current context takes precedence"), `<decision_log>` (recent decisions), plus an entity **directory** (bounded: `max_entities_in_directory=50`, `max_entities_in_context=5`, `max_facts_per_entity=10`, `max_events_per_entity=5`; truncation is visible in the rendered context; facts carry dates so stale vs. current is distinguishable).
- **Namespaces:** `"user"` (private; v3 embeds a `user_id` digest into row keys and re-keys pre-v3 rows via migration — this fixed a real cross-user leak), `"global"` (default), custom (`"engineering"`, `"sales_team"`).

**Access & management:** everything reachable programmatically via `agent.learning_machine.<store>.get/search/print(...)`, via AgentOS REST (memory CRUD endpoints), and in the Control Plane UI. **Curator** (`lm.curator.prune(max_age_days=...)` / `deduplicate()`) exists but currently operates on a `memories` field of the User Profile that the default schema doesn't define — effectively a no-op unless you add that field yourself (documented warning).

**Team memory:** `update_memory_on_run=True` on a `Team` runs the MemoryManager over each team run; `Team with Memory Manager` reconciles user memories with latest input; "Team with Agentic Memory" lets the team update memories mid-run. Learning machines attach to teams the same way.

### 4.3 External memory integrations (mem0, Zep, Memori)

- **Mem0** — `Mem0Tools(user_id=..., api_key=...)` toolkit (`agno.tools.mem0`): `add_memory`, `search_memory`, `get_all_memories`, `delete_all_memories`; runs the Mem0 Platform with `MEM0_API_KEY` or a **local `Memory` instance** without a key. Per-function enable flags. Docs flag adapter drift: `search_memory`/`get_all_memories` still pass a top-level `user_id` while the current Mem0 Platform API requires entity filters; constructor `user_id` overrides `RunContext.user_id`. This is a **toolkit-level** integration (the model calls mem0 tools) — native Agno memory does not run through mem0, and the mem0 example pattern injects retrieved memories as dependencies/context rather than replacing the store.
- **Zep** — `ZepTools` (store/retrieve/search memory data); the integration pattern writes user messages through Zep, waits for sync, passes the retrieved Zep context block in as a dependency.
- **Memori** — registers against the agent's OpenAI client with a SQLite-backed store.
- Takeaway: external memory services are bolted on as tools/dependencies, not as storage backends. The native path is always the `db` + stores.

## 5. Agent Storage & Resume

**One `db` interface for everything.** A single `db` parameter on Agent/Team/Workflow/AgentOS persists: sessions (`agno_sessions`), runs (`agno_runs` — new in v3), memories (`agno_memories`), learnings (`agno_learnings`), knowledge metadata (`agno_knowledge`), traces/spans, approvals, schedules + schedule runs, metrics, eval runs, components + configs + links, service accounts, durable jobs (`agno_jobs`), tool-result offload index (`agno_tool_results`).

- **Backends (12 + async variants):** Postgres, SQLite, MySQL, Mongo, SingleStore, Redis, Valkey, DynamoDB, Firestore, Json (file), GCS-Json, InMemory. Vector side separate: 19 vector DBs. Recommended production pairing: `PostgresDb` + `PgVector` (one Postgres for state + embeddings).
- **Per-component db override:** each agent/team/workflow can take its own `db` overriding the AgentOS default — the documented tenant-isolation / hot-agent-isolation pattern.
- **v3 runs-table migration:** runs were previously a JSON blob inside the session row (O(N²) write amplification, DynamoDB/Firestore item-size ceiling). v3 normalizes runs into `agno_runs` with real columns (`session_id`, `run_type`, `agent_id`/`team_id`/`workflow_id`, `user_id`, `parent_run_id`, `status`, `run_index`); `MigrationManager(db).up()` is idempotent and non-destructive; stale DBs raise typed `MigrationRequiredError`/`SchemaMismatchError`.
- **Storage control:** `store_media` (default True), `store_tool_messages` (True — disabling removes tool-call/result pairs AND the assistant messages that issued them), `store_history_messages` (False). **Media offloading** (v3): `media_storage=S3MediaStorage/GCS/Local` uploads media to object storage and keeps a small `MediaReference` (a 113 KB JPEG drops ~151k chars → ~2,897). **Tool-result offloading** (v3): results > 16,000 chars go to AgentFS with an envelope + `read_result`/`search_result` tools.

**Session model:** `run_id` (per execution) / `session_id` (groups runs = thread) / `user_id` (owner). `session_state={...}` is app-managed state persisted with the session (carts, task lists, workflow progress — distinct from memory and history). History to context is opt-in (`add_history_to_context`, bounded by runs or messages).

**How "resume" works — three distinct mechanisms:**

1. **Conversation continuation (no special API):** a new run with the same `session_id` + `db` loads prior runs/messages; history and session state rehydrate. Runs re-attach on read.
2. **HITL pause/resume (the real resume system):** a run pauses with `active_requirements` (confirmation, user input, external tool execution, admin approval); requirement objects expose `.confirm()/.reject(feedback)/.set_user_input(...)`; then `agent.continue_run(run_id=..., requirements=...)` or `continue_run(run_response=...)` (sync/async/streaming; teams and workflows have their own `continue_run`, with `member_agent_name` on team requirements). Continuation **requires the same database and session identity**; pause state is persisted so resume survives process restarts. v3 changed `continue_run` to take `requirements` (list of `RunRequirement`) instead of `updated_tools`. Workflow pauses surface as `WorkflowRunOutput` + `StepRequirement` (step-level) or executor requirement dicts.
3. **Background/durable execution:** accepted background runs are committed `agno_jobs` rows — they survive crashes/restarts/deploys and any replica picks them up; cancellable while queued; `Idempotency-Key` dedupe; queue REST surface for requeue/stats.

**Caveat for external frameworks:** Agno persists its *own* run/session records for adapter agents, but framework-native resume is not guaranteed — e.g. the Claude adapter keeps its SDK resume-session mapping **in process memory**; external-framework agents stream inline for `background=true` and are **not resumable**.

## 6. Notable Extras

- **Evals** (`agno.eval`): `Case(input, criteria, expected_tool_calls, scorer)` + `cli()` — nonzero exit code gates CI. Types: Accuracy (LLM-as-judge), Agent-as-judge (custom rubric), Reliability (expected tool calls/args — refused/errored/HITL-rejected calls never satisfy), Performance (latency/memory), and in-process **Scorers** (v2.8): `CodeScorer` (any callable), `JudgeScorer` (LLM judge, normalized), `ToolCallScorer` (deterministic tool-execution checks). Production evals via background post-hooks; results in `agno_eval_runs` with per-run `run_id` (v3 fix: re-runs no longer overwrite).
- **Environments** (v2.8, `agno.environments`): `Environment` + `Task` + `run_rollouts(env, k=8)` — pass@k rollouts in full isolation (fresh db/session/user, no memory/knowledge/learning writes), drift-vs-policy fingerprints, and `to_sft_jsonl()` exporting passing attempts as conversational SFT data with provenance. This is the "turn your agent platform into a learning loop" story.
- **AgentOS runtime:** FastAPI-based; ~50+ endpoint groups — runs (create/list/cancel/**continue paused runs**/resume disconnected streams, SSE or background), sessions, memory (CRUD + search + topic filter + **optimization endpoint**), learnings, knowledge (upload from files/text/URLs/S3/GCS/SharePoint/GitHub; vector/keyword/hybrid search; content status), evals, traces (filter DSL, span trees), metrics (daily aggregates, per-model breakdown), schedules, approvals, **versioned components**, service accounts, database migrations. MCP server at `/mcp` (8 curated tools after the v2.7 security shrink). JWT auth + RBAC scopes + multi-user/multi-tenant isolation; interfaces: Slack, Telegram, WhatsApp, Discord, AG-UI, A2A.
- **Control Plane / Studio:** web UI (os.agno.com connects to your runtime) — compose components from a Registry, **draft → publish → promote/rollback** with CAS guards and tombstoned deletes (Studio 3.0), inspect trace trees (model calls, tool I/O, delegation, steps, tokens, latency), search knowledge, **review/edit user memories**, resolve approvals, manage schedules, switch local/staging/prod runtimes.
- **Reasoning:** three patterns — native reasoning models (`reasoning_effort`, `reasoning_summary`), `ReasoningTools` (`think`/`analyze` structured notes in the tool loop), and a separate `reasoning_model` stage (own model; doesn't inherit tools). `reasoning=True` removed in v3.
- **Structured output/input:** `response_model` (Pydantic) for agents/teams; validated structured input; per-step structured I/O in workflows; JSON mode.
- **Context Providers:** a sub-agent-mediated tool surface per data source (Slack, Gmail, Calendar, Drive, SQL DB with separate read/write engines, Filesystem, Web, MCP, Git/Notion wiki, read-only project Workspace). Exposure modes: `default` (`query_<id>` + `update_<id>` with separate read/write sub-agents — the read sub-agent *cannot* call write tools), `agent` (single query tool), `tools` (raw toolkit). Keeps source-specific tool sprawl out of the calling agent.
- **CodeMode** (v3): replaces a wide tool schema with one persistent IPython kernel — model writes Python composing tools as awaitable handles.
- **Guardrails** (PII detection, prompt injection, OpenAI moderation), lifecycle hooks, cron scheduling with persisted history/retries, OTel observability (12+ exporters) plus first-party traces in your db.
- **Coding-agent-first distribution:** deploy templates (agentos-railway/docker/aws/gcp/azure/fly/render/modal/helm) set up by handing a prompt to Claude Code/Cursor/Codex; docs served as an MCP server (`docs.agno.com/mcp`) and `llms.txt`; `agnoctl` CLI (`agno connect`) mints scoped PATs and writes MCP config into Claude Code, Claude Desktop, Cursor, Codex, ChatGPT.

## 7. Verdict — what's worth borrowing for a platform that centrally manages knowledge + memory across MANY heterogeneous agents (incl. external coding-agent CLIs)

### Borrow these patterns

1. **One typed persistence interface, many domain tables.** A single `db` abstraction (12+ backends, sync+async) behind *every* subsystem — sessions, runs, memories, learnings, knowledge metadata, traces, approvals, schedules, evals, metrics, components. For a central platform this is the core architectural move: memory and knowledge stop being per-agent concerns and become tables in *your* database that every agent reads/writes through one interface. Also borrow the v3 lesson embedded in it: **normalize runs out of session blobs early** (they hit O(N²) write amplification and document-DB size ceilings at scale and had to migrate everyone).

2. **Memory as multiple typed stores behind one small protocol** (`recall` / `process` / `build_context` / `get_tools`). The six-store taxonomy is the single best borrowable idea here: structured **User Profile** vs. unstructured **User Memory** as separate stores; **Session Context** as a replaced-not-appended snapshot (goal/plan/progress — explicitly designed for handoffs and history truncation); **Entity Memory** as a typed fact/event/relationship graph with supersession and archival; **Learned Knowledge** as cross-user insights in the same vector store as documents; **Decision Log** with outcome recording for feedback loops. A central platform can offer these as managed services every agent plugs into, and the uniform protocol makes adding a store (or swapping a backend per tenant) cheap.

3. **Per-store capture modes: Always / Agentic / Propose.** Always-mode extraction running **concurrently with the main call from the input snapshot** (off the response path) is a clean way to get passive capture without latency; agentic tools for deliberate writes; propose for reviewable writes. Their honest docs on the tradeoffs (extra call per store per run; agentic misses implicit info; propose is prompt-only) are themselves a useful design checklist.

4. **Context injection as tagged, bounded, inspectable blocks.** `<user_profile>`, `<session_context>`, `<relevant_learnings>` etc., with per-store render limits (50-entity directory, 5 expanded entities, 10 facts), visible truncation, and dated facts so staleness is detectable. Bounded injection is what keeps a central memory service from blowing up every agent's context — and the tags make memory behavior debuggable in traces.

5. **Cross-agent memory sharing by construction.** Same db + same `user_id` = shared memories across all agents/teams/workflows, with no per-agent wiring. For a platform, invert Agno's default: agent-scoped memory should be the namespace, not the silo. Agno's namespace model (`user` / `global` / custom like `"engineering"`) plus the v3 fix (embed a `user_id` digest into row keys — they shipped a real cross-user leak before this) is the blueprint.

6. **Resume as a first-class persisted contract.** Pause state in the db; resume via explicit **requirement objects** (`confirm / reject(feedback) / set_user_input / select`) and `continue_run(run_id, requirements)`; durable background jobs as committed rows executed by any replica, with idempotency keys and bounded concurrency; "Redis is optional coordination, never truth." If the platform orchestrates long-running coding agents, this requirements-object pattern — a typed, resolvable record of *why* a run stopped — is directly reusable, including for surfacing "agent needs approval" to a central UI (`agno_approvals` + audit trail).

7. **Versioned components with draft → publish → rollback** (Studio 3.0: DRAFT serves nobody until publish, CAS guards with typed 409s, tombstoned deletes, dependent tracking). Central management of heterogeneous agent configs needs exactly this; per-version pinning on run requests ("run agent X version N") closes the loop for reproducibility.

8. **Evals + rollouts as the platform's learning loop.** `Case`-based CI-gating evals with reliability checks on *tool executions* (not just text), plus pass@k isolated rollouts that can export SFT data. A platform that centrally stores runs gets this almost for free and it's the strongest retention story Agno has.

9. **Context Providers' read/write separation** (read sub-agent physically cannot call write tools; separate DB engines). Any central platform exposing shared knowledge to untrusted/heterogeneous agents should copy the privilege split rather than relying on prompt instructions.

10. **Memory hygiene tooling as API surface.** A memory-optimization endpoint (summarize/compact with preview-before-apply), memory CRUD + search in REST and the admin UI, and a separate cheap model for memory ops. Note their gaps as requirements for your design: their Curator (prune/dedupe) doesn't actually operate on the default user-memory store, and Always-mode learned-knowledge dedupe ignores namespace filters (documented leak) — memory lifecycle management is where they're thinnest.

### Where Agno does NOT solve your problem (and what that implies)

- **External coding-agent CLIs are second-class by design.** `ClaudeAgent` (Claude Agent SDK) and the other adapters get registration, streaming, session records, and tool-call visibility — but **no team membership, no Agno memory/knowledge/delegation/hooks/skills, no structured I/O, no durable resume** (the Claude adapter's resume-session mapping lives in process memory). Agno's answer for reaching external agents is *outward*: serve memory/knowledge via REST + a curated MCP surface (and they deliberately shrank the MCP memory-CRUD tools to REST+PATs for security). For a platform that centrally manages memory/knowledge *for* external CLIs, the integration point must be the CLI's own extension surfaces (MCP servers the CLI connects to, rule/context files, hooks) — i.e., build a memory MCP server + context-file writer, not an SDK adapter. Agno's v2.7 decision (memory CRUD out of MCP, scoped PATs in REST) is a useful security precedent for how much surface to expose per interface.
- **Memory is user-centric, not agent-centric.** Five of six stores key on `user_id` or `session_id`; only the Decision Log is per-agent. A platform managing *operational* memory across many agents (per-agent facts, learned procedures, environment quirks) needs an agent/entity-scoped store Agno only partially provides (Entity Memory is closest, but it's about the user's world, not the agents').
- **Multi-agent coordination is leader-mediated only** (no peer-to-peer member calls; v1's collaborate mode removed). Route/coordinate/broadcast/tasks are clean, composable primitives worth borrowing as *labels*, but don't look here for deep orchestration theory — and don't let a central platform inherit the constraint that only native agents can be composed.
- **Governance gaps to learn from:** Propose mode is prompt-enforced (explicit warning not to use as sole approval control); memory-capture "instructions" (e.g. "don't store real names") are not validated on the write path; pruning is manual code. If your platform promises centralized memory governance, enforce it in the storage layer, not the prompt.

### Bottom line

Agno has evolved from a lightweight agent framework into a **vertically-integrated agent platform** (SDK + runtime + control plane + eval/training loop), and its most transferable IP for a central knowledge/memory platform is not the agents but the **plumbing**: the single-db-many-tables persistence spine, the typed multi-store memory architecture with per-store capture modes and bounded tagged context injection, namespace-scoped sharing with per-user key isolation, the persisted requirement/resume contract, and the versioned-component governance model. Its honest boundary — external-framework agents get serving but not memory/knowledge — defines exactly the gap a platform for heterogeneous coding-agent CLIs must fill itself: expose the central memory/knowledge services through protocols those CLIs already speak (MCP, REST, context files), rather than expecting SDK-level adoption.
